## 2. 오늘 진행한 관련 작업의 맥락

### 진단 스프레드시트

별도 Google Sheets 진단 문서에서 메뉴 구조와 통계의 사용 흐름을 정리했다. 해당 문서 자체는 이 저장소의 산출물이 아니며, 공개 저장소에 문서 식별자·고객사별 대상 목록·실제 진단 데이터를 저장하지 않는다.

- 진단 메뉴는 1·2·3 Depth이며, 1 Depth만 있는 메뉴도 정상으로 처리한다.
- 메뉴 경로는 입력된 단계를 합쳐 표시한다.
- 시트 연결 상태, 메뉴 등록 상태, 결과 입력 상태, 취약점 판정을 서로 구분한다.
- 메뉴 수·평가항목 수·입력 칸 수를 구분한다.
- 위험도는 5·4·3·2·1을 각각 집계한다.
- 샘플 및 중복 등록 행이 통계에 섞이는 문제를 정리했다.
- 반복 메모를 제거하고 공통 안내를 대표 셀 한 곳으로 통합했다. 평가항목별 설명은 유지했다.
- 취약 결과는 진한 빨강, 취약 건수·경로는 연한 빨강, 입력·연결 오류는 주황 계열로 보완했다. 0건·빈칸은 강조하지 않는다.

이 경험을 이번 프로그램에도 반영한다. 결과를 단순히 많이 수집하는 것뿐 아니라 사용자가 어떤 항목을 확인하고 어디에 붙여넣을지 이해할 수 있어야 한다.

## 3. 사용자와 확정한 요구사항

### 목표

사이트의 실제 메뉴 구조를 수집하고 **엑셀에 전체 메뉴 구조를 매핑**한다. 처음 언급된 "하위도메인 3단계"는 DNS 도메인이 아니라 메뉴 단계라는 점을 확인했다.

예: `조회 → 계좌조회 → 거래내역조회`.

### 최대 3단계

초기에는 3단계 초과 경로를 별도 확인 대상으로 보존하는 방안을 고려했으나, 사용자가 **"3단계 넘는 경로는 3단계까지만 하면 됨"**으로 범위를 확정했다.

최종 기준:

- 결과의 메뉴 단계는 최대 3개다.
- 4단계 이하의 메뉴명과 목적지 URL을 별도 메뉴로 내보내지 않는다.
- 여러 하위 메뉴가 같은 3단계 아래에 있으면 해당 3단계 분류를 대표로 남긴다.
- 4단계 페이지 URL을 3단계 메뉴의 URL인 것처럼 붙이지 않는다.
- 실제 3단계 메뉴 자체의 URL이 발견되면 주소 없는 대표 분류보다 우선한다.
- 1단계·2단계에서 끝나는 정상 메뉴는 그대로 둔다.

### 로그인 및 미수집 항목

- 로그인 뒤에만 나타나는 내용이 수집되지 않았다면 별도로 표시해야 한다.
- 로그인·접근 권한·접속 실패·동적 메뉴·구조 확인 대상을 정상 수집과 분리한다.
- 로그인하지 않으면 이름 자체가 드러나지 않는 메뉴를 추측해서 만들지 않는다. 해당 페이지의 미수집 사유를 기록한다.
- 사용자가 브라우저에서 로그인하고, 열린 화면을 추가하거나 다시 수집하는 흐름을 목표로 한다.
- 실제 자격증명은 받은 적이 없고, 로그인 시험도 하지 않았다.

### 엑셀

- 최종 파일 형식은 `.xlsx`다.
- 전체 메뉴 목록에는 URL과 발견 근거를 남긴다.
- 진단 시트용 붙여넣기 표에는 1·2·3 Depth 메뉴명만 둔다.
- 기존 진단 시트 배치에 맞춰 H13:H15부터 가로로 메뉴를 배치한다.
- 한 묶음은 H:IW의 250개 메뉴이며, 초과하면 다음 `진단메뉴_02` 등에 나눈다.
- 원본 수집 목록과 사용자가 검토·수정한 붙여넣기 목록을 구분한다.
- 임의의 취약점 판정을 생성하지 않는다. 이 프로그램의 상태는 수집 상태다.

### 사용 환경

- 우선 Windows PC에서 로컬 실행하는 방향으로 구성했다.
- 이는 앞선 대화 환경을 바탕으로 잡은 기본 가정이며, Windows 버전·실행 권한·배포 형식은 아직 확정 응답이 없다.
- 실제 검증용 사이트 주소 및 로그인 필요 여부를 요청했으나 아직 전달받지 않았다.

## 4. 작성한 코드

| 파일 | 현재 역할 |
|---|---|
| `menu_crawler/models.py` | 수집 설정, 메뉴, 결과 모델. 1단계 메뉴 및 3단계 분류의 매핑 가능 여부 |
| `menu_crawler/urls.py` | HTTP(S) 정규화, 추적 쿼리 제거, SPA hash 경로 보존, 호스트 범위 검사, 일부 민감 쿼리 가림 |
| `menu_crawler/extract.js` | 메뉴 DOM·중첩 목록·일부 ARIA 연결·현재 경로·열린 shadow root를 읽는 스크립트 |
| `menu_crawler/crawler.py` | Playwright 브라우저 세션, 프레임 읽기, 링크 탐색, 중복 정리, 3단계 제한, 수집 상태와 사유, 작업 스레드 |
| `menu_crawler/export.py` | 요약·전체 메뉴·확인 필요·방문기록·진단 붙여넣기 엑셀 생성 |
| `menu_crawler/web.py` | 로컬 API 초안. 세션 토큰, 작업 제어, 상태 조회, 엑셀 응답 |
| `launcher.py` | 로컬 포트를 먼저 확보한 뒤 실행 화면을 여는 진입점 초안 |
| `menu_crawler/static/.gitkeep` | 향후 화면 파일 위치. 실제 UI는 아직 없음 |
| `tests/test_foundation.py` | URL·정책·3단계 제한·메뉴 별칭·엑셀·API·브라우저 DOM 기본 검증 |

### 수집 방식

- 기본적으로 시작 호스트만 방문한다. 다른 호스트는 사용자가 명시적으로 추가하는 방식이다.
- URL의 `/` 개수를 메뉴 단계로 사용하지 않는다.
- 실제 메뉴 DOM에서 읽은 구조를 우선하고, 일반 본문 링크는 구조 검토 대상으로 분류한다.
- 같은 URL이어도 메뉴 경로가 다르면 별도 메뉴로 유지한다. 방문 요청은 URL 기준으로 중복을 줄인다.
- 주소가 없는 동적 메뉴는 임의 실행하지 않고 확인 대상으로 남긴다.
- 임의의 업무 버튼 클릭·폼 제출은 하지 않는다. 일부 메뉴는 hover 방식으로 읽는다.
- HTTP 상태, 최종 주소, 로그인 화면 추정, 탐색 제한, 프레임 읽기 실패 등을 기록한다.
- 페이지 수, 시간, 링크 이동 횟수 제한을 별도로 둔다. 링크 이동 횟수는 메뉴 단계와 다르다.

### 로컬 API 초안

| 경로 | 역할 |
|---|---|
| `GET /api/status` | 수집 상태와 현재 결과 |
| `POST /api/open` | 설정에 맞춰 새 브라우저 세션 시작 |
| `POST /api/control/crawl` | 수집 시작·재수집 |
| `POST /api/control/capture` | 사용자가 열어 둔 화면 읽기 |
| `POST /api/control/stop` | 현재 요청 종료 후 중지 요청 |
| `POST /api/control/close` | 세션 종료 |
| `POST /api/export` | 선택한 메뉴와 함께 엑셀 다운로드 |

API는 실행 시 생성된 로컬 세션 토큰을 요구한다. 실제 UI가 이 API를 호출하는 연결은 다음 작업이다.

### 데이터 처리

- 결과와 로그인 브라우저 세션은 현재 프로세스 메모리에 둔다. 영구 세션 저장 기능은 없다.
- 흔한 인증 토큰·세션 ID·인증 코드 쿼리는 표시·내보내기 단계에서 가린다. 모든 사이트의 임의 파라미터를 식별하는 기능은 아니다.
- 수집한 문자열은 엑셀에서 수식으로 실행되지 않도록 문자열 셀로 기록한다.
- 실제 대상 사이트 목록, 진단 내용, 로그인 정보, 다운로드한 엑셀은 저장소에 넣지 않는다.

## 5. 미완성 및 다음에 확인할 사항

### 아직 없는 기능

- 사이트 주소·옵션 입력 화면.
- 수집 시작·중지·현재 화면 추가 버튼과 진행 표시.
- 수집 결과 필터·메뉴 단계 수정·포함 여부 선택 화면.
- 실제 사용자 엑셀 다운로드 흐름.
- Windows 실행용 배치 파일, 설치 안내, 실행 파일 패키지.
- 실제 대상 사이트에 맞춘 메뉴 선택자·탐색 보완.

### 구현 검수가 필요한 부분

- 로그인 후 재수집 시 이전 미수집 경고가 남는지, 해결된 경고의 이력을 어떻게 표시할지 정해야 한다.
- 시각적으로만 계층이 표현된 div 기반 메뉴와 복잡한 ARIA/포털 메뉴는 현재 일반 추출기로 정확히 매핑되지 않을 수 있다.
- 접속 가능한 페이지와 실제 메뉴 전체를 수집한 상태를 혼동하지 않도록 UI·엑셀 표현을 검수해야 한다.
- 동적 버튼, 클릭해야 생성되는 메뉴, 사용자 권한별 메뉴는 실제 사이트에서 확인해야 한다.
- 다중 탭·프레임·로그인 리다이렉트·SPA·중지 후 재수집의 전체 흐름은 아직 시험하지 않았다.
- 페이지 수 제한과 별도로 후보 메뉴 수가 과도하게 늘어나는 경우의 제한을 검토한다.
- 선택한 3단계 분류가 독립 페이지 없는 그룹인 경우, 사용자가 진단 대상으로 채택할 수 있도록 표시를 명확히 해야 한다.
- 메뉴 이름만 바뀌거나 같은 경로에 여러 주소가 있을 때 엑셀 중복의 의미를 검토한다.

## 7. 마감 검증

검증 결과는 아래 마감 기록에 이어 적는다. 기능 완성을 뜻하는 것이 아니라 현재 초안의 기본 검증이다.

- Python 구문 컴파일: 통과.
- 초기 pytest: 8개 통과, 브라우저 테스트 1개는 Linux의 `libatk-1.0.so.0` 누락으로 실행 실패.
- Playwright Chromium 및 필요한 Linux 시스템 의존성을 설치한 뒤 재실행: **9개 테스트 모두 통과** (`9 passed, 1 warning`, 6.23초).
- 의존성 검사 `python -m pip check`: 통과 (`No broken requirements found`).
- 테스트 항목: 메뉴 쿼리·SPA 경로 보존, 표시 URL의 인증 값 가림, 호스트·로그인·파일·상태 변경 링크 분류, 4단계 제외와 3단계 대표 항목, 1단계 메뉴와 동일 URL의 복수 메뉴 경로, 엑셀 문자열 처리와 250개 분할, 수동 수정 매핑, 로컬 API 세션 및 엑셀 응답, 실제 headless Chromium에서 숨겨진 중첩 메뉴 읽기.
- 테스트는 합성 데이터와 로컬 브라우저 문서로 수행했다. 실제 외부 진단 대상에 대한 접속 시험은 하지 않았다.
- 남은 테스트 경고 1건: Starlette TestClient가 `httpx` 대신 `httpx2` 전환을 안내하는 deprecation warning. 현재 테스트 성공에는 영향이 없으며 후속 의존성 정리 때 확인한다.
- 실제 대상 사이트 로그인 및 Windows 환경: 검증하지 않음.
- 사용자 화면: 미구현이므로 화면 검수 대상 없음.
